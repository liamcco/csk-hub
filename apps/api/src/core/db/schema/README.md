# Drizzle schema

The application's tables, defined once per supported database:

```text
postgres/   the PostgreSQL schema: drizzle-kit generates `drizzle/` from it, and its types are the
            application's types
mariadb/    the same tables for MariaDB: drizzle-kit generates `drizzle-mariadb/` from it
*.ts        one selector per module, which is what the application imports
```

Application code imports `@/core/db/schema/<module>` and never a dialect folder. A selector
exports the tables of the process's dialect (`databaseDialect` in `../dialect.ts`, decided by the
connection string's scheme) typed as the PostgreSQL tables, so feature code has one set of types
and one set of queries. On MariaDB those queries run on Drizzle's MySQL builders, which
`../mariadb/compat.ts` gives the PostgreSQL methods the features use.

## Keeping the two in step

A change to a table changes both folders in the same commit, with a migration for each:

```bash
bun run db:generate --name=add-something          # drizzle/, from postgres/
bun run db:generate:mariadb --name=add-something  # drizzle-mariadb/, from mariadb/
```

Each MariaDB table names the same columns with the same JavaScript keys, so a row reads the same on
either database. The spellings differ where MariaDB needs them to (`./mariadb/columns.ts`):

| PostgreSQL | MariaDB |
| --- | --- |
| `uuid`, `defaultRandom()` | `varchar(36)`, generated by the application |
| `text` that is a key, indexed or unique | `varchar(255)` |
| `timestamp`, `timestamptz` | `datetime(3)` in UTC |
| `jsonb` | `json` |
| `pgEnum`, the Voice domains | inline `enum`s |
| partial and NULLS NOT DISTINCT unique indexes | unique indexes over invisible generated columns, hand-written in the migration |
| a composite primary key a feature maps by name | a unique index with PostgreSQL's key name |

Constraint, index and foreign-key names are the same on both databases, because features map
violations by name.
